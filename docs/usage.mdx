# Using `solana-trading-api` from your backend

A signing-agnostic library: build a `Trade`, call `quote` / `swap`. It picks the
venue, derives the pool, builds + simulates the tx, and signs via *your* `Signer`
(Turnkey). Marked `publish = false`, so it can never reach crates.io.

---

## 1. Keep it private

Neither option touches a public registry.

**Path dependency (monorepo / local) — simplest:**
```toml
# backend/Cargo.toml
[dependencies]
solana-trading-api = { path = "../solana-trading-api" }
```

**Private git dependency (separate private repo):**
```toml
solana-trading-api = { git = "ssh://git@github.com/<you>/solana-trading-api.git", tag = "v0.1.0" }
```
Authenticate with SSH + `git-fetch-with-cli = true` in `~/.cargo/config.toml` (or a
deploy key / PAT in CI). Cargo fetches the source to build; it stays in your repo.

You also need `async-trait`, `anyhow`, and `tokio` in your backend.

## 2. The whole flow

```rust
use solana_trading_api::{TradingClient, Trade, Venue, RpcClient, BloxrouteSubmitter};
use std::sync::Arc;

let rpc = Arc::new(RpcClient::new("https://your-rpc".into()));
// The client just holds RPC + Jupiter config. Submitter, priority fee, and tip are per swap.
let client = TradingClient::new(rpc, "https://api.jup.ag", Some(jupiter_api_key));

// Build a request — only what you know. Pool is derived from the mint.
let trade = Trade::buy(wallet, mint, 1_000_000, 500, Some(Venue::PumpFun)); // 0.001 SOL, 5%
// venue is Option<Venue>: Some(PumpFun)/Some(PumpSwap), or None → straight to Jupiter
// (or Trade::sell(wallet, mint, token_amount, slippage_bps, venue))

// Preview
let quote = client.quote(&trade).await?;        // { in_amount, expected_out, min_out, fee }

// Execute (signer = your Turnkey impl, see §3). Submitter (how it lands, §4) + priority fee
// are PER swap. The tip rides on the submitter (set it with `.with_tip`, §4).
let blox = BloxrouteSubmitter::fast(blx_host, blx_auth);          // carries its own tip; reuse across swaps
let result = client.swap(&trade, &signer, &blox, 50_000).await?;  // { hash, dex, status, amount_received }
```

That's it. Notes:
- `amount` is **SOL lamports** for a buy and **base tokens** for a sell. PumpSwap
  automatically bridges through USDC when the selected pool is USDC-quoted.
- The **pool is derived** from the mint per venue. Override for a non-canonical / USDC
  PumpSwap pool with `Trade::buy(...).with_pool(pool)` or `Trade::sell(...).with_pool(pool)`.
- On a **Pump.fun pre-send failure** (e.g. the token graduated), the client
  **falls back to Jupiter** automatically. PumpSwap never uses Jupiter. The fallback is
  **pre-send only** — once the tx is broadcast, a confirmation hiccup is never retried,
  so it can't double-send. Jupiter isn't a selectable `Venue` — pass `venue: None` to
  route straight to it.
- `result.status` is `Confirmed` / `Failed` / `Pending` (didn't confirm before the deadline).
- Errors come back as a typed **`TradeError`** (§6), not a string — `match` it to pick an HTTP status.

### SOL-funded buy from a USDC PumpSwap pool

Use the two-hop PumpSwap route when the target pool accepts USDC but the user is
paying with SOL:

```rust
let trade = Trade::buy(wallet, mint, 1_000_000, 500, Some(Venue::PumpSwap))
    .with_pool(usdc_target_pool);

let quote = client.quote(&trade).await?;
let result = client
    .swap_with_lookup_tables(
        &trade,
        &signer,
        &blox,
        50_000,
        &pumpswap_route_lookup_tables,
    )
    .await?;
```

The pool's on-chain `quote_mint` selects this route automatically. `amount` is
the maximum SOL spend in lamports. It atomically buys
an exact amount of USDC from the configured PumpSwap USDC/WSOL pool, then spends
all of that USDC in the target pool. This route never falls back to Jupiter.

For a sell, use the same API and lookup tables:

```rust
let trade = Trade::sell(wallet, mint, token_amount, 500, Some(Venue::PumpSwap))
    .with_pool(usdc_target_pool);
```

This atomically sells tokens for USDC, spends the first leg's guaranteed minimum
USDC on the bridge, and unwraps the resulting WSOL into native SOL. The user does
not need an existing USDC balance, but still needs SOL for fees and account rent.
Any USDC received above that minimum remains in the wallet; the bridge does not
spend pre-existing USDC. Sell quotes return `expected_out` and `min_out` in SOL
lamports based on the fixed bridge input. For both routed buys and sells, `fee`
reports only the bridge fee in lamports, not the combined fees of both legs.
Slippage is split between the legs, with at most 50 bps allocated to the bridge.

Run the read-only mainnet sell simulation (no private key or broadcast):

```sh
cargo test --lib simulate_sell_from_usdc_pool -- --ignored --nocapture
```

The test uses the shared `DG8Y7fV6NaiFBu1LfjNquqbqcPFAVvFA8uP1DhCVC5vb` table,
checks sell-only transaction size, then simulates a buy followed by the two-hop sell
to seed the fixture wallet with tokens. It verifies that WSOL is unwrapped and
pre-existing USDC is preserved. Live pool state and table availability can change.

The two PumpSwap instructions exceed Solana's packet size without address
compression. Pass one or more on-chain address lookup tables containing the
shared PumpSwap accounts and pool accounts; oversized transactions return a
build error before signing. The default bridge pool is `DEFAULT_SOL_USDC_POOL`
and can be replaced with `TradingClient::with_pumpswap_sol_usdc_pool`.

Create one shared Pump.fun/PumpSwap lookup table with the included example. Put the
authority's base58 keypair in the ignored `.env` file, optionally with a private
RPC endpoint:

```dotenv
PRIVATE_KEY="base58-keypair"
RPC_URL="https://your-mainnet-rpc"
```

Preview the shared addresses without loading the key or sending a transaction:

```bash
cargo run --release --example create_shared_alt -- --dry-run
```

Create the table once:

```bash
cargo run --release --example create_shared_alt
```

This sends one create transaction plus one or more extend transactions and pays
their rent and fees from that keypair. It reads current fee recipients from both
venues and includes global/config/event/volume accounts, common programs, WSOL/USDC
mints and fee ATAs, the default bloXroute tip recipient, and the fixed SOL/USDC bridge
accounts. Set `PUMPSWAP_SOL_USDC_POOL` only if using a different bridge in the client.

No target mint, target pool, or trading wallet is required. Those varying accounts
remain inline in each transaction. The keypair controls and funds the table; all
trading wallets can use it. Invoked program IDs and signers remain inline even when
listed in the table. The executor still checks each transaction's final byte size.

The script waits for activation and prints `ALT_ADDRESS=...`. To resume an interrupted
creation or append newly configured fee recipients/bridge accounts to the same table:

```bash
cargo run --release --example create_shared_alt -- --table YOUR_ALT_ADDRESS
```

It checks authority and table capacity and only appends missing addresses. No table
update is needed when trading a different target token. The creation/extension flow
uses Solana's [address lookup table instructions](https://solana.com/developers/cookbook/transactions/lookup-tables).

Before creating a table, the script checks payer funding for the full list's additional
rent and estimated transaction fees. Creation selects a slot from the `SlotHashes`
sysvar. If an extension fails, fund the payer if necessary and resume with the table
address already printed; rerunning without `--table` may create another table.

Load the printed address and pass it to the swap:

```rust
use solana_trading_api::load_address_lookup_table;

let shared_alt = load_address_lookup_table(rpc.as_ref(), alt_address).await?;
let result = client
    .swap_with_lookup_tables(&trade, &signer, &blox, 50_000, &[shared_alt])
    .await?;
```

### Submit-now: return the hash before it confirms

`swap` blocks until the tx confirms (or the deadline). For a low-latency response —
hand back the signature the instant it's broadcast, then check landing separately — use
`submit` and poll `status(hash)`:

```rust
use solana_trading_api::SwapStatus;

let pending = client.submit(&trade, &signer, &blox, 50_000).await?; // { hash, dex, status: Pending }
println!("submitted {} via {}", pending.hash, pending.dex);     // hash + venue known immediately

// later, by hash (e.g. from a GET /swap/status/{hash} endpoint):
match client.status(&pending.hash).await? {
    SwapStatus::Confirmed => { /* landed — parse the tx for the fill */ }
    SwapStatus::Failed    => { /* landed but reverted */ }
    SwapStatus::Pending   => { /* still in flight — poll again */ }
}
```

`submit` skips the confirmation wait **and** the two pre-send balance reads, so it returns
as fast as the submitter accepts the tx; `amount_received` is `None` (read it off the
landed tx). `result.dex` is the venue that **actually** built it — `"pumpfun"`,
`"pumpswap"`, or `"jupiter"` — so it reflects the fallback (a Pump.fun trade that lands via
Jupiter reports `"jupiter"`). `status` is a single poll at `confirmed` commitment — call it
until it's no longer `Pending`. Same venue routing + Jupiter fallback as `swap`.

## 3. Implement `Signer` with Turnkey

The library hands you an **unsigned** transaction; you return the wallet's signature.
This is where your Turnkey backend plugs in:

```rust
use async_trait::async_trait;
use solana_trading_api::{Signer, Pubkey, Signature, VersionedTransaction};

struct TurnkeySigner { /* turnkey client, sub-org id, signer key, … */ }

#[async_trait]
impl Signer for TurnkeySigner {
    async fn sign(&self, wallet: &Pubkey, tx: &VersionedTransaction) -> anyhow::Result<Signature> {
        // serialize tx.message, call Turnkey `sign_transaction` (type SOLANA, signWith =
        // wallet, organizationId = that user's sub-org) so your policies apply, return the sig
        todo!("call turnkey_client here")
    }
}
```

Use `sign_transaction` (not `sign_raw_payload`) so your on-chain policies can inspect the tx.

## 4. Choosing the submitter (MEV / non-MEV)

The submitter is the **3rd arg to `swap` / `submit`** — pass one per trade (construct it
once and reuse, or vary it per request). Pick one:

```rust
use solana_trading_api::{BloxrouteSubmitter, RpcSubmitter, SubmitProtection};

RpcSubmitter::new(rpc.clone())                       // plain RPC, non-MEV
BloxrouteSubmitter::fast(host, auth)                 // bloXroute staked RPCs, no protection
BloxrouteSubmitter::mev(host, auth)                  // front-running protection (SP_MEDIUM)
    .with_protection(SubmitProtection::High)         //   stronger: wait 8 safe slots
```

`host` is a regional bloXroute host (e.g. `"http://ny.solana.dex.blxrbdn.com"`); `auth` is
your Authorization header. `Submitter` is a trait, so more landing paths (Jito, etc.) slot
into `crate::submit`.

**bloXroute tips are automatic.** Both `fast` and `mev` carry their own tip —
`BloxrouteSubmitter::DEFAULT_TIP_ACCOUNT` + `MIN_TIP_LAMPORTS` (0.001 SOL) — via
`Submitter::default_tip` — so it's applied automatically, no per-swap arg. The tip is a real
transfer out of the wallet, so size the balance for it. Change the amount / rotate wallets on
the submitter: `BloxrouteSubmitter::fast(host, auth).with_tip(account, lamports)` — vary the
submitter per trade to vary the tip. Plain `RpcSubmitter` has no tip, so non-MEV sends never tip.

## 5. Priority fee

The last arg to `swap` / `submit` — **per swap** (e.g. bid a fat fee to win a snipe):

```rust
let result = client.swap(&trade, &signer, &blox, 200_000).await?; // big priority fee for THIS trade
let result = client.swap(&trade2, &signer, &blox, 50_000).await?; // smaller for the next

client.deadline = std::time::Duration::from_secs(60); // confirmation deadline (default 30s)
```

- `priority_fee_lamports` is the **total** priority fee, spread across the compute units
  (sized by a pre-send **simulation**, ×1.2, fallback default). Pass `0` to skip it.
- The **tip is on the submitter**, not here — it's submitter-specific (account + amount), set
  with `BloxrouteSubmitter::with_tip` (§4). To vary the tip per trade, vary the submitter.

**Lower level:** the venue builders are public — `dex.swap(&trade)` returns the raw
`(Vec<Instruction>, Vec<AddressLookupTableAccount>)` for a single venue (no fallback, no send).

## 6. Errors

Every fallible call returns `Result<T, TradeError>` — a typed error, not a stringly
`anyhow` blob. Each `Display` reads as a finished sentence (e.g. `config: invalid jupiter
URL "…" — relative URL without a base`), and the variants let your API layer map a
failure to the right HTTP status instead of a blanket 400:

```rust
use solana_trading_api::TradeError;

fn http_status(e: &TradeError) -> u16 {
    match e {
        TradeError::Config { .. }                            => 500, // our misconfig (bad RPC/Jupiter URL)
        TradeError::Http { .. }                              => 502, // venue API non-2xx (Jupiter/bloXroute)
        TradeError::Network { .. } | TradeError::Rpc { .. }  => 503, // transport / RPC — retryable
        TradeError::Sign(_)                                  => 502, // your Signer (Turnkey) failed
        TradeError::Submit(_)                                => 502, // submitter couldn't land it
        _                                                    => 400, // Decode / Build / Venue
    }
}
```

Variants: `Config` (bad URL, caught before any request goes out), `Http { venue, status,
body }`, `Network`, `Rpc { context }`, `Decode`, `Build`, `Venue { venue, msg }` (an
**on-chain** builder — Pump.fun/PumpSwap — failed), `Sign`, `Submit`.

Jupiter is the fallback and is reached through the same `Dex` path, but **its typed errors
are preserved** — a Jupiter failure surfaces as `Http` / `Network` / `Config` / `Decode`
(e.g. a bad key → `Http { venue: "jupiter", status: 401 }`), *not* `Venue`. So your status
mapper can treat Jupiter HTTP failures as `502` rather than lumping them into the `400`
catch-all.

If your backend is on `anyhow`, `?` still works — `TradeError` implements
`std::error::Error`, so the messages just get legible.

## 7. Notes / limits

- **Token-2022 handled** — the right token program is detected per mint.
- **Jupiter needs an API key** (`api.jup.ag`) for the `/swap/v2/build` endpoint;
  `lite-api.jup.ag` (free) is v1-only.
- **PumpSwap cross-quote routing** — USDC pairs use the configured USDC/WSOL bridge
  for SOL-funded buys and SOL-output sells. Other quote mints are rejected.
  Pump.fun USDC-quoted curves are not covered by this PumpSwap route.
- **Flat fee estimates** (global bps), not tiered — quotes can differ from the
  program's dynamic fees; on-chain minimum-output checks still protect execution.
- **Confirmation is synchronous-with-deadline**: only `hash` is known at send time;
  `status` + `amount_received` come from the landed tx.
